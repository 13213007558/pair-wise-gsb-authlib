RFC 8628: OAuth 2.0 Device Authorization Grant
==============================================

.. meta::
    :description: Python API references on RFC 8628 DeviceAuthorizationEndpoint
        and DeviceCodeGrant with Authlib implementation.

.. module:: authlib.oauth2.rfc8628

This section contains the generic implementation of :rfc:`8628`. OAuth 2.0 Device
Authorization Grant is usually used when devices have limited input capabilities
or lack a suitable browser, such as smart TVs, media consoles, picture frames,
printers and etc.

The device and the user act in parallel. The device polls the token
endpoint, while the user approves the request in a browser on another device:

.. mermaid::

    sequenceDiagram
        autonumber
        participant Device as Client (device)
        participant User as User's browser<br/>(User Agent)
        participant AS as Authorization Server
        participant RS as Resource Server

        Device->>AS: POST /device_authorization
        AS-->>Device: 200 OK + device_code, user_code
        Note over Device: Shows user_code<br/>and verification_uri
        par Device polls
            loop Every interval seconds
                Device->>AS: POST /token (device_code)
                AS-->>Device: 400 authorization_pending
            end
        and User approves
            User->>AS: GET /active
            AS-->>User: 200 OK + form
            Note over User,AS: The user logs in<br/>and enters user_code
            User->>AS: POST /active (user_code, allowed)
            AS-->>User: 200 OK
        end
        Device->>AS: POST /token (device_code)
        AS-->>Device: 200 OK + access token
        Device->>RS: GET /api (bearer token)
        RS-->>Device: 200 OK + resource

1. The device requests a device code. :class:`DeviceAuthorizationEndpoint`
   handles this request.
2. The response contains ``device_code``, ``user_code``,
   ``verification_uri``, ``verification_uri_complete``, ``expires_in`` and
   ``interval``. The device shows ``user_code`` and ``verification_uri`` to
   the user.
3. The device sends
   ``grant_type=urn:ietf:params:oauth:grant-type:device_code`` and the
   ``device_code``. :class:`DeviceCodeGrant` handles this request.
4. While the user has not answered, the response is
   ``authorization_pending``. It is ``slow_down`` if the device polls too
   often, ``expired_token`` if the code has expired, and ``access_denied``
   if the user refused.
5. The user opens ``verification_uri`` in a browser. The application
   implements this endpoint.
6. The user logs in. The verification endpoint shows a form to enter
   ``user_code``.
7. The user submits ``user_code`` and approves or denies the request.
8. The verification endpoint saves the user decision.
9. The device polls again.
10. The user has approved: the response contains the access token.
11. The device calls the API of the Resource Server with the access token,
    in the ``Authorization: Bearer`` header.
12. The Resource Server returns the protected resource.

The ``/device_authorization``, ``/active``, ``/token`` and ``/api`` paths are
examples.

To integrate with Authlib :ref:`flask_oauth2_server` or :ref:`django_oauth2_server`,
implement the missing methods of the two classes:

1. :class:`DeviceAuthorizationEndpoint`
2. :class:`DeviceCodeGrant`

Device Authorization Endpoint
-----------------------------

Implement the two missing methods:

.. code-block:: python

    from authlib.oauth2.rfc8628 import DeviceAuthorizationEndpoint

    class MyDeviceAuthorizationEndpoint(DeviceAuthorizationEndpoint):
        def get_verification_uri(self):
            return 'https://example.com/active'

        def save_device_credential(self, client_id, scope, data):
            credential = DeviceCredential(
                client_id=client_id,
                scope=scope,
                **data
            )
            credential.save()

    # register it to authorization server
    authorization_server.register_endpoint(MyDeviceAuthorizationEndpoint)

``get_verification_uri`` is the URL that end user will use their browser to
log in and authenticate. See below "Verification Endpoint".

After the registration, you can create a response with:

.. code-block:: python

    @app.route('/device_authorization', methods=['POST'])
    def device_authorization():
        return server.create_endpoint_response('device_authorization')

Device Code Grant
-----------------

With Authlib ``.register_grant``, we can add ``DeviceCodeGrant`` easily.
But first, we need to implement the missing methods:

.. code-block:: python

    from authlib.oauth2.rfc8628 import DeviceCodeGrant

    class MyDeviceCodeGrant(DeviceCodeGrant):
        def query_device_credential(self, device_code):
            return DeviceCredential.query(device_code=device_code)

        def query_user_grant(self, user_code):
            data = redis.get('oauth_user_grant:' + user_code)
            if not data:
                return None

            user_id, allowed = data.split()
            user = User.query.get(user_id)
            return user, allowed == '1'

        def get_polling_store(self):
            return redis_polling_store

    authorization_server.register_grant(MyDeviceCodeGrant)

Note ``query_user_grant``, we are fetching data from redis. This data
was saved from verification endpoint when end user granted the request.

Polling state contract
~~~~~~~~~~~~~~~~~~~~~~

While the user has not answered, the device polls the token endpoint every
``interval`` seconds. Authlib combines every check for one poll into the
:class:`DevicePollingStore` contract, so the storage backend can execute it
atomically:

.. autoclass:: DevicePollingStore
    :members:

.. autoclass:: PollingAdvance
    :members:

.. autoclass:: PollingVerdict
    :members:

The grant resolves each poll in a fixed order, independent of the order in
which the storage callbacks happen to run:

1. an expired ``device_code`` returns ``expired_token``;
2. a ``device_code`` that already produced an access token returns
   ``invalid_grant``, so one grant cannot be consumed twice;
3. a saved user decision is terminal: denial returns ``access_denied`` and
   approval returns the user. The decision is checked *before* the rate
   limit, so a poll that arrives too early still gets the token when the
   user approved at exactly the same time;
4. otherwise the poll is rate-limited atomically. An early poll returns
   ``slow_down`` and the interval grows by :data:`SLOW_DOWN_STEP` (5)
   seconds for this and every later poll; any other poll returns
   ``authorization_pending``.

Because :meth:`DevicePollingStore.check_and_advance` reads and writes the
state in one operation, two polls that arrive at the same time cannot both
be admitted against the old interval: one is admitted, the other gets
``slow_down``. A relational database serializes the operation with a row
lock; a Redis backend typically implements it with a Lua script.

The clock is injected and defaults to :func:`time.monotonic`, which makes
the state machine deterministic in tests without waiting real seconds:

.. code-block:: python

    from authlib.oauth2.rfc8628 import DeviceCodeGrant
    from authlib.oauth2.rfc8628 import InMemoryDevicePollingStore

    class MyDeviceCodeGrant(DeviceCodeGrant):
        def __init__(self, request, server):
            super().__init__(request, server, clock=my_clock)

        def get_polling_store(self):
            return InMemoryDevicePollingStore(clock=my_clock)

:class:`InMemoryDevicePollingStore` is the reference implementation. It is
thread-safe and suitable for a single-process server and for tests; a
multi-process deployment needs a shared backend implementing the same
contract.

Migrating from ``should_slow_down``
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Older applications only implemented ``should_slow_down`` and tracked the
interval themselves. That hook still works: when :meth:`get_polling_store`
returns ``None`` (its default), the grant falls back to the old behavior and
emits a deprecation warning. The compatibility boundary is therefore:

- no store, ``should_slow_down`` implemented: legacy behavior, deprecated;
- a store returned from :meth:`get_polling_store`: the contract enforces the
  interval, the ``slow_down`` increase and single use of a device code, and
  ``should_slow_down`` is never called.

Migrate by moving the polling timestamps and interval into a
:class:`DevicePollingStore` and returning it from :meth:`get_polling_store`;
the other methods of the grant do not change.

Verification Endpoint
---------------------

Authlib does not provide this endpoint. Here is a hint on how to implement
it:

.. skip: next "depends on the application login, templates and storage"

.. code-block:: python

    @app.route('/active', methods=['GET', 'POST'])
    @login_required
    def verify_device_code():
        if request.method == 'GET':
            return render_template('verification.html')

        allowed = request.form['allowed'] == 'yes'
        user_code = request.form['user_code']
        key = 'oauth_user_grant:' + user_code
        redis.set(key, f'{current_user.id} {int(allowed)}', 12)
        return render_template('verification.html')

Check points:

1. route should match ``get_verification_uri`` in Device Authorization Endpoint
2. user grant should match ``query_user_grant`` in Device Code Grant
